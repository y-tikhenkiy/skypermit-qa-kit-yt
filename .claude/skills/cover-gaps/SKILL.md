# Закриття прогалин у покритті

Скіл бере правила, яких ще ніхто не покрив, створює для кожного один кейс і лишає в `test-cases/` лише ті, що пройшли незалежну перевірку. Причина такого порядку: кейс, який створив той самий агент, що й перевіряє, підтверджує власні припущення. Тому перевіряє окремий субагент `tc-verifier`, який нічого не редагує. Кейс із хибним або вигаданим очікуванням гірший за відсутність кейсу, бо створює хибну впевненість.

`../skypermit` строго read-only. Усе, що створює цей скіл, лежить лише в цьому репозиторії.

## Аргументи

`/cover-gaps [максимум] [гейт]`, у будь-якому порядку:

- **максимум**: ціле число, скільки правил узяти за запуск. За замовчуванням `5`. Обмеження існує, бо кожне правило це створення кейсу плюс окрема верифікація.
- **гейт**: `PILOT`, `AIRCRAFT`, `ZONE`, `TIME_WINDOW`, `REGISTRATION` або `ALL` (за замовчуванням). `REGISTRATION` це правило `OH-1 §3` (вага понад 30 000 г при реєстрації літака), яке не є гейтом.

Якщо аргумент не розпізнано (слово не з цього списку), скажи про це й зупинись, а не вгадуй.

## Крок 1: список прогалин

З кореня репозиторію:

```
node .claude/skills/cover-gaps/scripts/uncovered-rules.mjs --max <N> --gate <GATE>
```

Скрипт друкує JSON: `groups` (прогалини, згруповані за гейтом), `selected` (правила цього запуску в порядку PILOT → AIRCRAFT → ZONE → TIME_WINDOW → REGISTRATION), `deferred_open_questions` (правила, які вже у відкритих питаннях і повторно не пропонуються), `warnings`. Кожне правило має `id` (`<ГЕЙТ>:<rule_reference>`), `condition`, `rule_reference` і `notes` з уточнень `07-clarifications.md`.

Правило вважається покритим, якщо якийсь кейс у `test-cases/` називає і його `failing_gate`, і його `rule_reference`. Це евристика за текстом. Ключ складається з пари, бо `ZC-2026.1 §2` спільний для `AIRCRAFT` і `ZONE`, і лише `failing_gate` їх розрізняє.

Якщо скрипт завершився з кодом 2, покажи користувачу його stderr і зупинись. Якщо `selected` порожній, перейди одразу до підсумку. Якщо `warnings` не порожній, перекажи їх користувачу: вони означають, що документи змінились, а примітки в скрипті могли застаріти.

## Крок 2: один кейс на правило

Обробляй правила **послідовно**, по одному. Паралельне створення дало б однакові номери `TC-GATE-NNN`, бо `test-case` визначає наступний номер за наявними файлами.

Для кожного правила запускай субагента (Agent, `subagent_type: "general-purpose"`, `model: "sonnet"`), який викликає скіл `test-case` (інструмент Skill) із запитом на **один** кейс: порушення правила й очікувана відмова. Модель фіксована, бо це структурована робота за шаблоном, а перевіряє результат сильніша модель (див. крок 3). Межі й позитивні варіанти не потрібні: ціль цього скіла в тому, щоб кожне правило мало хоч один кейс. У запиті вкажи:

- гейт, умову й `rule_reference` з JSON, а також розділ документації (`docs/06-business-rules.md` §1.x і §6);
- `notes` правила, якщо вони є;
- що в Expected result мають стояти буквально `failing_gate: "<ГЕЙТ>"` і `rule_reference: "<значення>"` (для `REGISTRATION` лише `rule_reference` і `422`). Без цього скрипт не побачить покриття й правило пропонуватиметься знову.

Запам'ятай шлях створеного файлу й ID: перелічи `test-cases/*/TC-*.md` до і після виклику.

Якщо `test-case` відмовився створювати файл, бо документація не визначає очікування (він так робить свідомо), не примушуй його. Перейди до обробки «документація мовчить» нижче з `case_id: null` і без верифікатора.

## Крок 2.5: механічний лінт

Для кожного нового кейсу, до верифікатора:

```
node .claude/skills/cover-gaps/scripts/lint-case.mjs <файл> --gate <ГЕЙТ> --rule "<rule_reference>"
```

Код виходу `0` — іди далі. Код `1` — видали файл кейсу (точний шлях, створений у цьому запуску), не виправляй і не викликай верифікатора; запиши в `rejected` причину з `problems`. Код `2` — покажи stderr і зупинись. Лінт дешевий і детермінований: він відсіює кейси без обов'язкових полів і без буквальних `failing_gate`/`rule_reference`, за якими скрипт покриття впізнає правило.

## Крок 3: верифікація

Коли кейси пройшли лінт, запусти по одному субагенту `tc-verifier` на кожен новий кейс (Agent з `subagent_type: "tc-verifier"`, у запиті ID кейсу). Їх можна запускати паралельно в одному повідомленні: вони лише читають.

Прочитай рядок `Вердикт:` у відповіді кожного й дій так:

- **відповідає**: кейс лишається.
- **не відповідає**: видали файл кейсу (`rm` на точний шлях, створений у цьому запуску) і не намагайся виправляти. У підсумок запиши причину зі стислої «Рекомендації» верифікатора. ID не перевикористовується: так вимагає `test-case`.
- **документація мовчить**: видали файл кейсу й додай запис у `test-cases/open-questions.md`. Кейс без визначеного очікування лише «перевіряв» би припущення.

Видаляй тільки файли, створені в цьому запуску. Жодних інших файлів у `test-cases/` не чіпай.

### Формат `test-cases/open-questions.md`

Якщо файлу нема, створи його із заголовком `# Відкриті питання за результатами cover-gaps`. Далі лише дописуй, нічого не перезаписуй. Один запис на правило:

```
## <id правила>

**Rule:** <id правила>
**Що не визначено:** <одне-два речення з вердикту верифікатора>
**Джерела:** <файл і розділ документації з відповіді верифікатора, плюс `docs/05-open-questions.md` чи `docs/07-clarifications.md`, якщо стосується>
**Кейс-кандидат:** <ID видаленого кейсу або «не створювався»>
```

Рядок `**Rule:** <id>` має бути точно в такому вигляді: за ним скрипт упізнає правило й не пропонує його знову.

## Підсумок

Після кроку 3 ще раз запусти скрипт із тими самими аргументами й візьми з нього `uncovered_total` як `remaining_gaps`. Останнім повідомленням поверни JSON у блоці коду без розлогих пояснень:

```json
{
  "args": {"max": 5, "gate": "ALL"},
  "selected": 3,
  "kept": [{"rule": "PILOT:OH-1 §2.1", "case_id": "TC-GATE-001", "file": "test-cases/api/TC-GATE-001-....md"}],
  "rejected": [{"rule": "ZONE:OH-1 §4", "case_id": "TC-GATE-002", "reason": "..."}],
  "open_questions": [{"rule": "ZONE:ZC-2026.1 §4", "case_id": "TC-GATE-003", "question": "..."}],
  "remaining_gaps": 10,
  "warnings": []
}
```

`case_id` у `open_questions` може бути `null`, якщо кейс не створювався. Відхилені правила лишаються в `remaining_gaps` і наступний запуск запропонує їх знову; причину відхилення дивись у `rejected`.
